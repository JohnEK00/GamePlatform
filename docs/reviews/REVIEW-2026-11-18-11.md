## Summary

**Round 10 is fixed and nothing has regressed.** See the status table.

**F030 is secure on the points that matter most.**
- **XSS:** there is no XSS path. `linkifyPost` only returns segments, and `PostBody` renders them as React text and `<a href>`. A link is created only for a candidate that passes `isSafeProfileUrl`: printable ASCII, `http(s)://`, a plain host with a dot, no `@`, and at most 200 characters. The link text is always the URL itself, so a post link can't claim a different destination. Scratch runs confirmed this for these inputs:
  - `"><img onerror>` stays inside the href;
  - `javascript:` stays text;
  - `user@host` and `\@` tricks are rejected;
  - `,`-joined URLs stay text;
  - balanced `(…)` is kept and a trailing `.` is dropped.
- **Privacy:**
  - Attachments are resolved for each viewer in `posts_for`. Games must pass `visible_to(viewer)`, and collections must pass `visible_to(viewer, admin)`.
  - `summaries_for` builds collection covers only from games the viewer can see.
  - At create time, an unpublished game gets 422 and a non-public collection gets 422.
  - An unpublished game or a private collection therefore can't leak through a post, the feed or the composer preview.
  - `stats.posts` counts every post, which is correct because every post is public. The other stats reuse the visibility filters of their list endpoints.
- **Authorisation:**
  - `DELETE /api/posts/{id}` checks for 404, then that the caller is the author or an admin (403 otherwise), and then deletes the post and resolves its reports in one transaction.
  - `canDelete` uses the same rule.
  - `clearProfile` can only be reached through `admin_resolve_report` (`AdminUser`), and only for `user` reports, which the validity table enforces before the 409 check.

**The 0025 upgrade is safe.** I applied 0001–0024 with `node:sqlite` and `foreign_keys = ON`, then seeded `gamePublished` and `collectionUpdated` rows and deleted the top two ids, so `seq` is above `MAX(id)`. After 0025:
- the rows are identical;
- `sqlite_sequence` keeps `seq = 6`, so the next id is 7 and feed cursors stay monotonic;
- `foreign_key_check` is empty and `integrity_check` is `ok`;
- all five indices exist;
- a row with no target is refused by the new CHECK;
- deleting a game sets `posts.game_id` to NULL and keeps `attachment_type`;
- deleting a post or its author cascades the `postCreated` row.

The cap count plan is `SEARCH posts USING COVERING INDEX idx_posts_author_created (author_id=? AND created_at>?)`, and the profile page walks the same index without a temp B-tree. No table or trigger references `activity_events`, as ARCHITECTURE says.

**Caps:** `Limit::Post` runs before validation, as specified. The 25-in-24-hours cap is an `INSERT … SELECT … WHERE COUNT < 25` under `BEGIN IMMEDIATE`, so it is atomic. Both string timestamps use the millisecond `Z` format.

**Null `FeedItem.game` breaks nothing that renders.**
- On the server, every non-post branch of `get_feed` reads `game_id` as `Option` and skips rows without one.
- In the current client, `isKnownFeedItem` rejects any non-post item without a `game`, and `FeedItem` handles `postCreated` before it reads `item.game`.
- Older clients drop `postCreated` as an unknown kind. However, both old and current clients show **"Your feed is empty"** when a whole page is filtered out (M2).

**Findings:**
- The main new risk is **profile link labels (M1)**. A label is free text and is shown instead of the destination, so `github.com/mia` can point anywhere.
- Below that are character-set gaps (L1, L2), two small UI state bugs (L3, L4), a banner race (L5) and docs drift (L6).

Also noted, below the bar for a finding:
- **Stale CSS comment.** `styles.css:6138` still says the F024 thumbnail is "never taller than the stacked avatars", which the updated spec contradicts (frontend-dev, trivial).
- **Deleting posts frees cap slots.** Deleted posts stop counting toward the 25 cap. Combined with `Limit::Post` (10 per 10 min), an author can make up to about 1,440 posts a day by deleting each one. This is as specified (spec § 0.6, API step 6). Each deleted post's feed event cascades, so nothing is left behind.
- **Pasted whitespace.** The client rejects a body or label with a leading or trailing tab, because it checks the raw text before trimming, although the server would trim it. This is stricter by design (spec § 0.3 and the F028 note), but a pasted trailing tab gives a confusing message.
- **Feed scans on the Posts tab.** On the Posts tab, branches (a) and (c) of `FEED_SQL` still walk every followed actor's events and discard them by kind. This is the same cost as the existing single-kind tabs and is bounded by `idx_activity_actor_id`. A kind guard on each branch (for example `?4` containing a branch's kinds) would skip them.
- **Post action names.** The `Delete` and `⚑ Report` buttons on a post have no per-post context in their accessible names, which matches `CommentItem`'s Delete. A list of 20 posts gives 20 identical buttons in a screen reader's button list. `aria-label="Delete post by {name}"` would follow the Reply, Pin and Lock labels.
