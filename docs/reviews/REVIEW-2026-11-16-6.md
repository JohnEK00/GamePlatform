**Migrations 0015–0017 are correct.** I replayed them on a seeded 0014 database:
- **Data:** every row survived, including `reports` in rowid order. The two rebuilt notification tables are byte-identical to the originals.
- **Sequences:** the AUTOINCREMENT high-water marks are carried over, so the next id is 6001 after a deleted tail at 5900–6000.
- **Schema:** the FKs point at the renamed parent, with no `_new` leftovers. All indexes and the 0014 trigger are recreated, and `foreign_key_check` and `integrity_check` are clean.
- **Behaviour:** the trigger and cascades still work, a second pin is rejected by the unique index, and the mute write-path check uses `idx_notification_mutes_target`.
- The Rust test `f018::migration_upgrade_from_0016` checks the same properties for 0017.

**Collections keep private data private.** I found no leak of private collections or unpublished games:
- **Profile:** for anyone but the owner, it lists only public collections with at least one game the viewer can see.
- **Game shelf:** it shows only public collections.
- **Covers and counts:** these use only games the viewer can see. Items with an unavailable game reach only the owner, as `game: null`.
- **Reports:** reporting a collection requires being able to see it. Admins see private collections by design.
- **Probing:** writes return 404 before 403, so a private collection can't be probed.
- **Concurrency:** the caps, pin, mute and reorder writes run under `BEGIN IMMEDIATE` with guarded inserts.
- **Rate limits:** every new write endpoint is limited (`Collections`, `ThreadTools`, and `Notifications` for mutes).

**Leader election is correct.**
- **Exclusivity:** Web Locks guarantee a single leader per (server, user) scope.
- **Handover:** a closed or stopped leader releases the lock, and the next tab takes over. That tab polls at once if its count is stale.
- **Server or user switch:** the provider effect restarts with a new scope.
- **Followers:** they validate messages (version, userId, shapes, clamping). A watchdog covers a frozen or halted leader. OS notifications run only in the leader.
- **Polling cost:** one request per cadence per browser. A hidden leader keeps polling only while a visible follower pings it.

**New this round: two mediums.**
1. **The dev server exposes the database and an admin-capable API to the LAN (M1).** The user's `server.host: true` lets anyone on the LAN download the dev SQLite database through Vite's `/@fs/` route. The API is also exposed through the dev proxy, and the backend falls back to a JWT secret that is published in the repo.
2. **Remove has no confirmation, and its only recovery is a 5 s toast (M2).** The Undo button is out of reach for keyboard and screen-reader users. For unavailable games it always fails.

The other five findings are low.

  - Mutes are checked at write time, in both the insert and the tombstone-restore path.

  - **Stale events:** generation checks drop events from a previous session.
  - **No leader:** followers never schedule polls. A visible follower falls back to its watchdog (`max(3 × poll, 180 s)`).
  - **Shared counts:** `syncUnread` shares mark-read and mute counts. A 401 or 429 is never broadcast.

A cross-site attacker therefore can't make credentialed requests whose response length they could observe, so BREACH's precondition doesn't hold. Compressing `/api` JSON would also be safe and is an optional future gain. What is compressed is static or non-secret content, with weak ETags and `Vary` on 200 and 304 alike.

  - It feature-detects `gamepadLabel`.
  - It has no `fetch`, `postMessage` or `parent` access, and shares are throttled above the engine's 3 s minimum.
