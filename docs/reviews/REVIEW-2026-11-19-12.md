## Summary

**Round 11 is fixed and nothing has regressed.** See the status table.

**F031 authorisation is correct on every path I checked.**
- **Reply delete** (`post_replies.rs:316-337`): the order is 404, then the reply's author, the post's author or an admin (403 otherwise), then `remove_post_reply`. That function resolves open `postReply` reports and deletes the row in one transaction. `PostReply.canDelete` (`replies_from_rows`) uses the same rule and is false for anonymous viewers.
- **Report delete:**
  - The admin `delete` action on a `postReply` report goes through the same `remove_post_reply`.
  - `remove_post` now also resolves open `postReply` reports on the post's replies.
- **Lock and unlock** (`posts.rs` `check_lock_rights`): the order is 404, then author or admin (403 otherwise), then `Limit::ThreadTools`. `PUT` keeps the first `locked_at`.
- **Who can still reply when locked:** only the author and admins.
  - The pre-check gives everyone else 422.
  - The guarded insert re-checks the lock with `?8 = moderator`, so a lock that lands mid-request still stops a non-moderator, and an admin still gets through.
  - In the UI, `showForm` is `user && (!locked || post.canDelete)`, which is the same rule.
- **Heart on your own post:** `PUT` returns 422 `You can't heart your own post` after the 404 and rate-limit checks. `DELETE` on your own post is a harmless `{ hearted: false }`. `PostCard` makes the heart non-interactive for the author.

**Privacy:**
- **OS notifications never carry post or reply text.**
  - `notificationParts` for `postReply` and `postHeart` returns only the actor phrase and a fixed verb, with no title part.
  - `osNotificationsFor` → `osNotificationText` → `notificationText` never reads `excerpt`.
  - The excerpts (the newest live reply, or the post's first 140 code points) appear only in the in-app panel and page, as the spec says.
- **Creators count only published games.**
  - The CTE and `COUNT_SQL` both filter on `published = 1`, so `games`, `plays`, `firstPublishedAt` and `lastActiveAt` only use published rows.
  - `followers` is the public follower count, and `isFollowing` is about the viewer only.

**Correctness:**
- **Reply cap under concurrency.** The guarded `INSERT … SELECT … WHERE COUNT(*) < 200` runs inside `BEGIN IMMEDIATE`.
  - A two-connection `node:sqlite` run (`sql/cap.mjs`) shows: while A holds the write lock, B's `BEGIN IMMEDIATE` fails with "database is locked" (in the app, `busy_timeout` makes it wait). After A commits reply #200, B's guarded insert changes 0 rows.
  - With the post locked, a non-moderator insert changes 0 rows and a moderator insert changes 1.
  - `reply_count` equals `COUNT(*)` (200 = 200).
  - The only backend test of the cap runs sequentially (L4).
- **Counter triggers** (`sql/up26.mjs`):
  - two hearts plus one `INSERT OR IGNORE` duplicate gives `hearts = 2`;
  - three replies give 3, and each delete decrements;
  - deleting a user cascades their hearts and replies and decrements the counts on other users' posts;
  - deleting a post cascades its hearts, replies and both notification kinds;
  - `foreign_key_check` is empty after each step.
- **Notification grouping and withdrawal:**
  - `postReply` uses `Dedupe::None`, with one event per reply keyed by `post_reply_id`.
  - Deleting a reply cascades its event. The scratch run confirms that the `0014` trigger deletes the notification when its last event goes.
  - `postHeart` uses `Dedupe::Actor`. Un-hearting calls `retract_pool`, which only tombstones events in an **unread** notification. A re-heart restores the event without notifying again, and a heart after the notification was read doesn't notify again (the actor-dedupe `NOT EXISTS` spans read states).
  - `VISIBLE` passes for these kinds (`game_id` NULL), and `MUTED` never matches.
- **The 0026 dedupe rebuild is safe** (`sql/up26.mjs`). The upgrade applied 0001–0025 with `foreign_keys = ON`, seeded two pre-existing heart events plus `post` and `user` reports, then applied 0026. After it:
  - the events are intact and `integrity_check` is `ok`;
  - the new index is `(notification_id, actor_id, IFNULL(comment_id,''), IFNULL(screenshot_id,''), IFNULL(post_reply_id,''))`, which is strictly finer than the 0023 key, so existing rows can't collide;
  - `reports.target_post_id` was backfilled for the `post` report and left NULL for the `user` report.
  - The `DROP` and `CREATE` run inside sqlx's per-migration transaction.
  - `git log` shows 0026 has not been edited since `7715254`, so sqlx checksums stay valid.
  - The partial indices (`idx_notifications_post`, `idx_post_replies_reply_to`) do serve the FK cascades. In `sql/fkpartial.mjs`, a post delete takes 0.29 ms with them and 14.5 ms without; a user delete takes 1.5 ms with them and 22 ms without.

**Query cost of `/api/creators`: there is no index for it, and it does scan everything on every request (M1).**
- Each request groups every published game (the plan uses `idx_games_pub_new` for `published=?`, then table lookups and `USE TEMP B-TREE FOR GROUP BY`).
- It runs a correlated follower count for every creator, whatever the sort, and then sorts the whole set in a temp B-tree before `LIMIT`/`OFFSET`.
- Measured with 10,000 creators, 48,000 published games and 300,000 follows: 42–46 ms per request for every sort and every page. For comparison, `GET /api/games` page 1 takes 0.01 ms.
- The endpoint is anonymous and has no rate limit. ARCHITECTURE § F035 accepts this cost "if the catalogue grows", but nothing bounds it today.

**Accessibility:**
