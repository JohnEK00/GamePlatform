## Summary

**Round 9 is fixed and nothing has regressed.** See the status table. L8 is fixed in a different way from the one suggested: `browser_command` is now a pure function, so every OS branch is compiled and tested on Windows CI.

**F024 is correct, and privacy holds.**
- **Unpublished games:** the hook runs only after `rows == 1` and only when `game.published` was true at step 2. That is the same condition the F015 feed uses. Only the owner can post to an unpublished game, and the owner's own posts are skipped twice (by the hook condition and in `notify_pool`).
- **Captions:** they never reach a notification. `target_of`, `excerpt`, `threadId` and `collection` are `None` for the kind. The UI renders the summary, a decorative `alt=""` thumbnail and the 📷 glyph. The OS body is the summary.
- **Mutes and settings:** game mutes and the `screenshots` switch suppress both new rows and joins, because they are in the same `INSERT … SELECT … WHERE`. Thread mutes can't match, because `?9` is NULL and `MUTED` then only accepts `m.thread_id IS NULL`. `mute_game` marks unread rows read by `game_id`.
- **Cascade on delete:** I applied migrations 0001–0023 to an in-memory SQLite database with `node:sqlite` and checked each delete:
  - Deleting a screenshot removes its event through the FK, read or unread.
  - The `0014` trigger then deletes a notification that has no events left. The trigger fires for FK cascade actions.
  - Deleting the author's account cascades in the same way.
  - The FK lookup uses the partial index `idx_notification_events_screenshot`, because `screenshot_id = ?` implies the index's `IS NOT NULL` condition.
- **Dedupe index:** two events with the same `(notification, actor)` and different `screenshot_id`s both insert, and repeating one with `INSERT OR IGNORE` changes 0 rows. No other kind is affected, because they all store `screenshot_id` NULL.

**F023 follows its spec, with one same-step problem (M1).**
- **Event order:** the order within a step matches GAME_FORMAT:
  1. revert wins;
  2. then physical `textEvents`;
  3. then the pointer key, then pad A on the key the cursor was on at the start of the step, then the cursor move, then X, Y, LB and Start;
  4. then submit or commit.
- **Same-step capture:** this works. The keyboard starts taking input one step after it opens, so the A or tap that starts editing never types. Keyboard capture still covers keyboard actions, and the direction actions reach the keyboard cursor only through gamepad or mouse bindings.
- **Pause:** `cancelPointer` drops `pressKey` and all three repeat timers, and the keyboard stays open.
- **The M1 problem:** the pad buttons the keyboard uses (Start, X, Y, LB) still fire the game's actions bound to them. In the step where Start submits, `ui.editing` is already `null` once the field's call has run. The Menu & HUD template checks `pause` (bound to Start) after its menus, so a controller player who presses Start to confirm their name is sent back to the title screen.

**What assistive-technology users get from the keyboard panel (L1).**
- **Screen-reader users:** nothing. The panel is pixels on the canvas. Nothing announces that it opened, the keys have no names, and the typed text is never read out. Today the game iframe has a title, and the canvas can take focus but has no role or label. The engine doesn't write anything to the DOM for any widget, and the docs don't mention this limitation.
- **Physical-keyboard users:** nothing changes. Their first key hides the panel.
- **Gamepad and switch users:** they can use it fully, by sight.
- **Low-vision users:** labels use the theme font and size, the cursor has a 2-unit `focusColor` outline, and disabled keys are shown only by alpha 0.5.
- **Touch-only players (L2):** they can't revert an edit, because the panel has no Cancel key and a tap outside commits. Gamepad players can't move the caret.

**Contract drift is small.**
- The F024 desktop verification test the spec requires was never added (L3).
- The ui README doesn't list the new exports, and ARCHITECTURE names the command kind wrongly (L4).
- The CSS comment and spec § 2 say the 48 px thumbnail never makes the row taller than the avatars, but it does (L5).

Also noted, below the bar for a finding:
- **Holding A starts a DEL repeat without a press on DEL** (scratch test 2). If the cursor reaches `DEL` while pad A is still held from an earlier key, `DEL` starts repeating after 0.4 s. This matches the letter of GAME_FORMAT ("while pad A is held with the cursor on DEL"), but not the F012 rule that a key needs a press on itself. Players rarely navigate with A held. Requiring `aPressed && onDel` to arm the timer would close it.
- **A deleted newest shot doesn't move the item back.** After the newest screenshot of a group is deleted, `updatedAt` (and the item's position and `latestAt`) keep the deleted shot's time, while `screenshot` shows the next one. API § F024 says "a join moves `updatedAt`", which is still true. This is the same harmless effect as the F015 `createdAt` note in round 9.
- **The notification write adds to the POST's latency.** It is a second `BEGIN IMMEDIATE` transaction (after the F015 feed event) inside the 201 path. Under write contention, each one can wait up to `busy_timeout` (10 s) before the response. This is bounded and best effort, as specified. Moving both writes after the response, or into a spawned task, would take them off the request path.
- **`tests/f024.rs` doesn't cover every delete path in the spec.** Author-account deletion, admin deletion and report-resolve deletion aren't tested. All three go through `DELETE FROM screenshots` or the user cascade, which the `node:sqlite` reproduction shows work.
