## Summary

The round-1 fixes hold up. **13 of 15 are fixed. R2 and R12 are only partly fixed.** The R1 data-loss race is closed: a per-game in-process claim, a version-guarded `UPDATE` and old-version deletion after commit, with concurrency tests in `review_fixes.rs` and `f004.rs::r1_race_writes_one_version_row`.

The new features are well specified and well tested. Every new endpoint has integration tests, the migrations upgrade a v2 database cleanly, and nothing leaks unpublished games or user data. The game-facing leaderboard view is properly sanitised.

The main problems are **query cost on hot paths that grows with total data**:
- **Feed:** the feed query walks every published game's events and sorts them. It took 343 ms at 300k events, because the app never runs `ANALYZE`.
- **Leaderboards:** each read re-ranks every retained score of the game (378 ms at 10k players). A score submit does this three times.
- **Trending refresh:** it runs inline in read requests. Its `viewer_key` purge rescans all historical play events inside a write transaction (about 0.8 s per 1M rows).

The rest are low-severity issues: a11y, a game draining the viewer's rate-limit bucket, and docs drift.

## Checked and fine

- **Migrations 0003–0007 on a v2 database:**
  - They apply in order and none was edited after commit, so sqlx checksums are stable.
  - Adding the `VIRTUAL` generated column and indexing it works on SQLite ≥ 3.31.
  - The dropped index names exist in 0001.
  - `favorites_count` triggers aren't affected by `ON CONFLICT DO NOTHING`, and nothing uses `INSERT OR REPLACE` on favorites.
  - The backfills give the expected rows: one `gamePublished` per published game, and one `game_versions` row per game.
- **Privacy:**
  - The feed filters `g.published = 1`, `actor ≠ viewer`, and achievements still being defined, all at read time.
  - `/related` returns only published games, uses tag counts over published games only, and is not personalised.
  - Version history and notes follow game visibility, and only the owner can PATCH.
  - Anonymous viewer keys are a secret-keyed 64-bit hash of the IP and are purged after the window.
  - The in-game leaderboard view (`toLeaderboardView`) carries only rank, display name, score and `isMe`: no ids, avatars or tokens.
- **Races:**
  - **`gameUpdated` coalescing:** it runs inside the serialised replace transaction (a SAVEPOINT).
  - **`personalBest` and `achievementUnlocked` coalescing:** delete-then-insert in a write-first deferred transaction. SQLite serialises these via `busy_timeout`, so counts stay correct.
  - **Notes PATCH vs replace:** they touch different `(game_id, version)` rows. `INSERT OR REPLACE` only ever hits a new version number.
  - **`expectedVersion`:** checked after the claim and before extraction.
  - **Trending:** the single flight re-checks freshness after taking the lock.
- **Rate limits:** Leaderboard, Play, Follow, Feed and VersionNotes are wired as documented. `/related`, `/versions`, follower lists and `sort=trending` are documented as unlimited public reads. `sort=trending` with correlated subqueries took 2.9 ms over 5k games, which is acceptable.
- **Feed paging:** the cursor is the last *row* id, so skipped rows never stall paging. Coalesced items move to new ids. The client de-duplicates by id.
- **UI:**
  - Feed and VersionHistory render notes as plain text (`white-space: pre-wrap`, no HTML).
  - Loading, empty and error states exist for the feed, suggestions, related, version history and the leaderboard periods.
  - The Follow button's label names the action ("Unfollow X" on focus).
  - The replace dialog uses `useModal`, and keeps the chosen file and notes after a 409.
- **Tests:** every F001–F004 backend feature has integration tests (f001–f004.rs), including migration-backfill SQL, the R1 race with version rows, the rate limits and refresh failure. The UI has per-feature test files. The engine has 79/79 passing.
