Also noted, below the bar for a finding:
- **Stale `createdAt` after a delete.** API § F015 says an item's `createdAt` is "the latest post of that day". After the newest shot is deleted, the row keeps the deleted shot's time, and the item keeps its feed position. This is harmless, but the API sentence holds only until a delete. Consider "the time of the post that last moved the item".
- **"Load more" as a focus fallback while a request is in flight.** `FeedPage.focusAfter` can return the `disabled` Load more button (`disabled={state.loadingMore}`). Focusing it fails silently, so focus drops to `<body>`. It is rare (the user has to empty the last visible item during a load). `aria-disabled` would fix it, as on the profile.
- **The duplicate-row note in API § F015 implementation notes.** The writer's `DELETE` takes the write lock before reading, so concurrent posts serialise and duplicates can't occur in practice. If they ever did, an older duplicate on the *next* page would be shown again (the de-duplication is per page). The note is defensive and is fine as written.
- **`rundll32.exe` is resolved by name.** Rust's Windows `Command` searches the application directory before System32. An attacker who can write to the per-user install folder can already replace the app, so there is no privilege boundary. Using `%SystemRoot%\System32\rundll32.exe` would be a cheap hardening step.
- **The `?section=screenshots` scroll** runs when the game loads. Sections above the gallery that load later (leaderboard, versions) can push it down afterwards. F004's `?section=versions` behaves the same way.
- **The profile list** has no rate limit and uses OFFSET paging. The work is bounded by one author's screenshots (≤ 20 per game), and the endpoint is like the other public lists.
